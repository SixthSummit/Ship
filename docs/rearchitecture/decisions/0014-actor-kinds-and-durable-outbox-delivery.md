# ADR-0014: Explicit actor kinds and durable outbox delivery

- **Status:** Accepted
- **Date:** 2026-09-18
- **Scope:** Actor model, actor-kind access, transactional outbox composition, idempotency enforcement, retention
- **Related:** [ADR-0004](./0004-credential-actor-and-access-boundary.md) · [ADR-0006](./0006-executable-transaction-scopes.md) · [ADR-0008](./0008-authorized-tenant-capabilities.md) · [ADR-0010](./0010-declared-immediate-effects.md)

## Context

ADR-0004 defined an actor as a stable id plus an immutable permission snapshot, resolved from transport credentials. Scheduled work, outbox dispatchers, and verified third-party callbacks have no credential-backed end user, yet they must run through the same operation boundary. Without a declared kind, such work is either impersonated through a synthetic human actor or granted ambient trust that the graph cannot see.

ADR-0010 keeps immediate effects outside transactions and states that outbox delivery is composition rather than a kernel mode, leaving payload, retry, lease and reconciliation to each application. Applications then re-implement claim, lease, retry, dead-letter and retention logic with subtly different guarantees. Process-local `afterCommit` hooks remain tempting because they are simple, and remain rejected because they vanish on process failure.

Idempotency was similarly left to consumers, so a retried write could run twice or race an in-flight request without any operation-level declaration.

## Decision

### Actor kinds and least privilege

`OperationActor` carries a required `kind`: `human`, `system`, or `provider`.

- `human` actors are resolved from transport credentials; `operationActor()` defaults to this kind so existing resolvers keep working.
- `system` actors represent scheduled or framework-driven work such as an outbox dispatcher. System status grants no implicit privilege: permission checks, `systemAccess()` restrictions and tenant authorization (ADR-0008) apply per invocation exactly as for a human.
- `provider` actors represent an external party verified against a named provider id. They are constructed only after that verification step succeeds; the kernel ships the kind, not the verification transport.

`systemAccess()` admits only system actors and `providerAccess(id)` only provider actors of that provider. Both are enforced by `checkOperationAccess`, narrowed on the handler context, and projected into the application graph, client contract and OpenAPI. A separate `onBehalfOf` attribution field records the requesting user for audit on system and provider actors and is never consulted for authorization.

### Two operations joined by a durable outbox

Effects after commit use two operations. The transactional operation binds `outboxDependency(outbox)` and receives an `OutboxWriter` that records schema-validated intents through the active unit-of-work scope, so they commit or roll back with the business change. A separate `transaction: "none"` dispatcher operation with `systemAccess()`, generated by `defineOutboxDispatcher`, claims due intents under a lease, performs each intent's single declared effect through the effect provider, records completion, and otherwise schedules a bounded retry with exponential backoff before dead-lettering. ADR-0010 is unchanged: immediate effects remain rejected on transactional operations.

`defineOutbox` binds every intent to exactly one `effectDependency` token and to a consumer-owned `perform` function, so the graph shows which effect a dispatched intent will cause and the framework never interprets payload meaning. The compiler rejects writers outside write transactions, outboxes written without a dispatcher, intents no dispatcher covers, non-singleton or provider-hidden outbox bindings, and cleanup declared without retention.

`afterCommit` callbacks and process-local post-commit hooks are not provided. A callback lost to a crash is an invisible failure; a persisted intent is observable, retryable and reportable.

### Delivery guarantee

Delivery is at-least-once with deduplication, never exactly-once. A process that crashes after an external effect succeeds but before completion is recorded leaves the record claimed; the lease expires and another dispatcher performs it again. Consumers supply `dedupeKey` values to suppress duplicate intents within the retention window and keep their effect providers tolerant of repeated delivery. The framework tests this crash case explicitly rather than documenting it away.

### Idempotency declaration

An operation may declare `idempotency: { key, windowMs, store }`. The executor claims `key` through the bound `IdempotencyStore` before the handler runs: a `duplicate` claim replays the stored success result without running the handler, an `in-flight` claim fails with the stable framework code `IDEMPOTENT_IN_FLIGHT` (409), a `claimed` key runs the handler and records the result, and a failed handler releases the claim. For `read` and `write` operations the executor passes the unit-of-work scope, so a transaction-aware store records the claim and result atomically with the business change; concurrent claims then wait on the key instead of observing `in-flight`.

### Retention

An outbox may declare `retention: { completedMs, deadLetteredMs }`. `defineOutboxCleanup` generates a system-access operation that deletes completed records past `completedMs` and dead-lettered or discarded records past `deadLetteredMs`, never pending or claimed ones. Scheduling it on a single runner belongs to the job runner, not this decision.

## Consequences

- Scheduled and callback work is visible as its own actor kind in audit trails, graphs and contracts, and cannot silently inherit human or admin privileges.
- Applications compose durable delivery from framework-owned claim, lease, retry, dead-letter and retention primitives while keeping payloads, effect adapters and business retry policy.
- The dispatcher is an ordinary operation: it runs through the executor, can be invoked from tests with `drainOutbox`, and is subject to the same access rules as everything else.
- Duplicate delivery is a documented contract, so effect providers must be idempotent or deduplicate on their side.
- Idempotency is declarative and enforced identically for direct, HTTP and future transports.
- The cleanup operation is defined as `transaction: "none"` because a write transaction would require a unit-of-work binding the outbox has no knowledge of; each delete is individually atomic.
- Raw actor snapshots without `kind` are rejected, which is a breaking change during the alpha window.

## Rejected alternatives

### Implicit system trust

Rejected because a privileged system actor recreates the boolean bypass that ADR-0008 removed and hides cross-tenant work from audit.

### `afterCommit()` callbacks or post-commit hooks

Rejected, reaffirming ADR-0010: callbacks are lost on process failure and provide no retry, lease or reconciliation contract.

### Exactly-once delivery claims

Rejected because an external system cannot participate in the local transaction; claiming exactly-once would make the crash-after-effect case an undocumented duplicate rather than a tested one.

### A generic effect interface instead of per-intent `perform`

Rejected because it would force every effect provider to conform to a framework-shaped call signature and move payload meaning into the kernel.

## Addendum 2026-09-18: claim cost under a backlog and the adaptive dispatch runner (SAPI-114)

The accepted text above is unchanged. The M10 capacity baseline (SAPI-113
step 11, [docs/v4/capacity-baseline.md](../../v4/capacity-baseline.md)) found
two things about outbox dispatch at a sustained write rate: the Drizzle claim
slowed from about 240 rows/s at a 12k backlog to about 16 rows/s at 205k
pending rows, and the consumer's dispatchers at batch 25 every 250 ms
completed about 150 intents/s against 500/s written, so the backlog grew
without bound. This addendum records the diagnosis, the two framework-side
changes and the numbers.

### Claim cost grew with the backlog because the `OR` could not be served in index order

`(status = 'pending' AND available_at <= now) OR (status = 'claimed' AND
lease_expires_at <= now)`, ordered by `(available_at, created_at)` and took
`LIMIT batchSize FOR UPDATE SKIP LOCKED`. PostgreSQL cannot return an `OR` of
two status predicates in index order, so the planner fell back to a
sequential scan of every due row followed by a sort before the `LIMIT`. At
1k pending rows the sort is a quicksort in memory and the claim costs 0.26 ms;
at 200k it is an external merge sort on disk (9.4 MB of temp files per claim)
and the claim costs 76 ms, of which 43 ms is the scan and the rest the sort.

### What changed in `@sixthsummit/ship-drizzle`

`shipOutboxTable()` gains two partial indexes, one per claim branch, each
holding only the rows that branch can return in the order the claim takes
them:

```sql
CREATE INDEX "ship_outbox_pending_idx" ON "ship_outbox" ("outbox_id", "available_at", "created_at") WHERE status = 'pending';
CREATE INDEX "ship_outbox_lease_idx" ON "ship_outbox" ("outbox_id", "lease_expires_at") WHERE status = 'claimed';
```

The existing `ship_outbox_due_idx` and `ship_outbox_dedupe_idx` are unchanged.
The claim is restructured into two statements instead of one `OR`:
lease-expired claimed rows are retaken first (bounded by the batch size) so a
permanent pending backlog cannot starve them, then pending rows fill the
remainder. Each statement is an ordered index scan with `LIMIT` and
`FOR UPDATE SKIP LOCKED`, atomic on its own, so two dispatchers still never
claim the same row. The same plan at 200k pending rows after the change:

### Before and after claim latency

Measured by the new load-shaped test (`claimDue(now, 25, 30_000)` thirty
times after five warm-up claims, against a seeded backlog whose
`available_at` is spread over the last ten minutes, plus half as many
completed rows and ten lease-expired claimed rows; `VACUUM ANALYZE` and
`CHECKPOINT` after the seed; wall clock includes the pool round trips). The
test asserts the 200k p95 stays within five times the 1k p95 (25 ms floor), a
bound the previous claim missed by two orders of magnitude.

| pending rows | before p50 / p95 / max (ms) | after p50 / p95 / max (ms) |
| ---: | ---: | ---: |
| 1,000 | 1.69 / 2.33 / 2.53 | 4.51 / 6.68 / 7.86 |
| 200,000 | 70.94 / 74.00 / 77.86 | 4.80 / 11.29 / 13.04 |

The "after" small-backlog figure is higher than before because the claim is
now two round trips instead of one (the lease branch runs first and is
usually empty); the large-backlog figure is fifteen times lower and no longer
depends on the backlog. A claim of 25 rows costs about 5 ms on the reference
host at any backlog, so a single dispatcher claims about 5,000 rows/s before
the effect work is counted.

### The dispatcher runner is adaptive, and the graph can warn about declared under-capacity

The baseline's workers slept the dispatch interval after every round whatever
the round returned, so their capacity was `batchSize x rounds/s` and fixed.
`@sixthsummit/ship-core` now owns one dispatch loop for every outbox,
`startOutboxDispatchRunner(executor, "<outbox>.dispatch", { intervalMs?,
maxPassesPerCycle?, backoff?, observer?, onError?, actor?, signal? })`, and
`startRealtimePublicationRunner` is that loop over
`ship-realtime.publication.dispatch`. A pass whose claim filled the batch is
followed by the next pass at once, at most `maxPassesPerCycle` (default 10)
full passes back to back before the runner yields to `intervalMs` (default
1,000 ms); a short or empty pass waits the interval; a failed pass backs off
with the outbox backoff shape; `stop()` returns after the in-flight pass and
never starts another; one pass is in flight at a time per runner. Concurrency
stays bounded (one pass per runner, the dispatcher's batch per pass) and the
backpressure contract is unchanged: nothing is dropped, and an overflowing
backlog is still visible through the outbox health and the queue-lag monitor
rather than absorbed. So the runner can tell a full batch from a short one,
`OutboxDispatchResult` carries `batchSize` alongside the counts. The observer
seam receives every pass, so `createPublicationRunnerMetrics()` and any
observer built on `OutboxDispatchRunnerObserver` count the extra rounds
without change.

Two optional declaration fields make the shortfall visible at compile time
instead of in a capacity run. `defineOutbox({ expectedRatePerSecond })`
states the sustained rate the application expects to record, and
`defineOutboxDispatcher(outbox, { roundsPerSecond })` states the cadence the
application's runner drives the dispatcher at per process. When both are
declared the compiler projects `expectedRatePerSecond` and
`dispatchCapacityPerSecond` (`batchSize x roundsPerSecond`) on the outbox
graph node and emits the warning
`SHIP_OUTBOX_DISPATCH_CAPACITY_BELOW_PUBLISH_RATE` when the capacity is
below the rate. Neither field is required; an application that states
neither sees no change. `defineRealtimePublicationModule` accepts both for
the publication outbox.

seeded backlogs, the latency bound, the plans above);
`packages/kernel/src/outbox-runner.test.ts` (full batch followed at once,

`realtime-publication.test.ts` (the realtime runner over the shared loop);
the customized golden consumer's `bridge.startReportsDispatcher` drains a

## Addendum 2026-09-23: receipts with removed intent IDs (SAPI-426)

An outbox can contain receipts written by an older application version after
that version's intent declaration has been removed. Filtering every dispatch
claim to the current dispatcher intent IDs left those receipts pending forever.
They appeared in outbox health but never reached the existing failure path.

The dispatcher periodically probes for IDs absent from the **full** current
outbox declaration. An empty probe is followed by a five-second pause to
avoid scanning a healthy backlog on every dispatch pass. Once obsolete work
is found, dispatchers reserve one slot per batch and drain it continuously;
a batch of one alternates between current and unknown work. Unknown receipts are immediately
dead-lettered with their removed ID in `lastError`, without invoking an
effect. Operators can inspect, retry or discard them through the existing
dead-letter operations. A retry of an unchanged removed ID dead-letters again.
Current intents retain the rest of the batch, and a free reservation is filled
with current work.

`OutboxBackend.claimUnknownDue` is optional for compatibility with custom
backends whose single dispatcher covers every intent; these use an unfiltered
claim as a fallback. Under sustained current-intent backlog, that fallback's
unknown-ID progress depends on the backend's claim order; custom backends
should implement `claimUnknownDue` for bounded progress. A dispatcher that
handles only a subset of current intents requires the new method, because an
unfiltered claim could steal another dispatcher's valid work. `ship-drizzle`
and `ship-testing` implement the method. The Drizzle adapter uses the same bounded, ordered,
`FOR UPDATE SKIP LOCKED` claim path as current intents, with an inverse intent
filter. PostgreSQL integration tests cover persisted removed IDs, dead-letter
inspection and retry, and partition isolation.
